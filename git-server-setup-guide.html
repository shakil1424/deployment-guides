Backup & Navigate

Always backup before touching git

1
Find the project path
Server

If you don't know the exact path, search for it first.

bash 
# Search for project directory
find / -type d -name "<PROJECT_FOLDER>" 2>/dev/null

# Or list common webroot locations
ls /var/www/
2
Backup server code — DO NOT SKIP
Critical

Creates a timestamped copy of the entire project. If anything goes wrong, the backup is untouched.

bash 
cp -r <PROJECT_PATH> <PROJECT_PATH>_backup_$(date +%Y%m%d_%H%M%S)

# Verify both folders exist
ls -lh /var/www/<project-parent>/ | grep <project-folder>
💡 You must see TWO entries — original and backup — before proceeding.
3
Navigate into project
Server
bash 
cd <PROJECT_PATH>

# Confirm you're in the right place
pwd
ls
2

Fix .gitignore

Exclude secrets, uploads, and runtime files before staging

4
Check & update .gitignore
Critical

Check what's already excluded. Then add any missing entries. Never commit .env, vendor/, certificates, or upload files.

bash 
cat .gitignore
bash — edit if needed 
nano .gitignore
.gitignore — minimum required entries 
# Laravel defaults
/node_modules
/public/hot
/public/storage
/storage/*.key
/vendor
.env
.env.backup

# Runtime / cache
/storage/framework/sessions/
/storage/framework/cache/
/storage/framework/views/
/storage/logs/

# Uploads & user files
/public/uploads/
/uploads/

# SSL Certificates — NEVER commit these
/public/securefile/
*.crt
*.key
*.pem

# Archives
*.tar.gz
*.tar
*.zip
💾 Save in nano: Ctrl+O → Enter → Ctrl+X
5
Untrack already-tracked files that should be ignored
Server

If uploads, certs, or storage files were previously committed, remove them from git's index (files stay safe on disk).

bash 
# Untrack common directories
git rm -r --cached public/uploads/ 2>/dev/null
git rm -r --cached public/securefile/ 2>/dev/null
git rm -r --cached storage/framework/views/ 2>/dev/null

# Untrack common files
git rm --cached .env 2>/dev/null
git rm --cached *.crt *.key 2>/dev/null

# Verify no sensitive files remain staged
git status | grep -E "\.env|\.key|\.crt|\.pem|securefile|uploads"
✅ The grep should return nothing. If it does return something, remove it with git rm --cached <file>

Initialize Git & Commit

Only if git doesn't exist. Skip git init if already initialized.

6
Initialize git (skip if already exists)
If no git
bash 
# Check if git already exists
ls -la | grep .git

# If NO .git folder exists, initialize
git init

# Set global identity (use org email)
git config --global user.name "ServiceHub Dev"
git config --global user.email "mizanur.rahman@paystation.com.bd"

# Allow this directory (fixes ownership errors)
git config --global --add safe.directory <PROJECT_PATH>
7
Stage & commit all server code
Server

Review what's staged before committing. Make sure no .env or certificates appear in the list.

bash 
git add -A

# Review staged files — check for secrets!
git status

# Commit
git commit -m "chore: init commit from production server <REPO_NAME>"
4

Deploy Key Setup

SSH deploy key so server can push/pull without passwords

8
Generate SSH deploy key on server
Server
bash 
ssh-keygen -t ed25519 -C "<KEY_COMMENT>" -f ~/.ssh/<KEY_NAME>
# Press Enter twice (no passphrase)

# View the public key to copy to GitHub
cat ~/.ssh/<KEY_NAME>.pub
🔑 Copy the entire output line starting with ssh-ed25519 AAAA...
9
Add deploy key to GitHub
GitHub

Manual steps in browser

  1. Go to github.com/<ORG_NAME>/<REPO_NAME>/settings/keys
  2. Click "Add deploy key"
  3. Title: <DEPLOY_KEY_TITLE>
  4. Key: paste the public key
  5. ✅ Check "Allow write access"
  6. Click "Add key"
10
Configure SSH to use deploy key
Server
bash 
nano ~/.ssh/config
~/.ssh/config — add this block 
Host <SSH_ALIAS>
    HostName github.com
    User git
    IdentityFile ~/.ssh/<KEY_NAME>
    IdentitiesOnly yes
bash — test connection 
ssh -T <SSH_ALIAS>
# Type 'yes' when prompted
# Expected: Hi <ORG_NAME>/<REPO_NAME>! You've successfully authenticated...
5

Remote & Branch Setup

Connect to GitHub and push server code to release branch

11
Set GitHub remote
Server

If a remote already exists with old URL, remove it first. Then add the new SSH remote using the alias.

bash 
# Remove old remote if exists
git remote remove origin 2>/dev/null

# Add new SSH remote using alias
git remote add origin git@<SSH_ALIAS>:<ORG_NAME>/<REPO_NAME>.git

# Verify
git remote -v
12
Fetch remote & create release branch
Server
bash 
# Fetch remote (safe — no file changes)
git fetch origin

# Check current branch name
git branch

# If branch is 'master' or 'main', rename to 'release'
git branch -m master release
# OR if already on a named branch, create release from it
git checkout -b release
13
Force push server code to GitHub release branch
Critical

This overwrites the remote release branch with server code. Server code wins. This is intentional.

bash 
git push origin release --force

# Set upstream tracking
git branch --set-upstream-to=origin/release release

# Final verify
git status
✅ Expected: On branch release — Your branch is up to date with 'origin/release'. nothing to commit, working tree clean
6

Developer Workflow

What developers do locally after server push

14
Sync local machine to new release branch
Local

Since we force-pushed, the remote release history changed. Run this on local machines to sync.

powershell / bash (local machine) 
git checkout release
git fetch origin
git reset --hard origin/release
⚠️
This discards local release history. If developer has uncommitted work on another branch, it's safe — only affects the release branch.
15
Create feature branch & start working
Local
powershell / bash (local machine) 
# Always branch off release
git checkout release
git checkout -b feature/your-feature-name

# Work, then commit & push
git add -A
git commit -m "feat: your change description"
git push origin feature/your-feature-name

# On server — pull latest release
cd <PROJECT_PATH>
git pull origin release

Branch naming conventions

  1. feature/payment-gateway — New features
  2. fix/login-error — Bug fixes
  3. hotfix/bkash-callback — Urgent production fixes
  4. dev-<name> — Personal dev branch (e.g. dev-shakil)
7

Developer Onboarding from Local Code

For developers who already have code locally — tracked or untracked — and need to sync with the new release branch

⚠️
Read this before running any git command. Identify your situation below first. Running the wrong flow can overwrite local work.
A
Scenario A — Already using Git, code is committed
Local

Your local code is already tracked by git and all changes are committed (no pending uncommitted files). You just need to pull release and branch off it.

bash / powershell — check your current state first 
# See which branch you're on and what's uncommitted
git status
git branch
bash / powershell — add remote and pull release 
# Add remote if not set yet
git remote add origin <REPO_SSH_OR_HTTPS_URL>

# Fetch all remote branches
git fetch origin

# Switch to release and sync
git checkout release
git pull origin release
bash / powershell — create your working branch 
# Branch off release — use a name that matches your work
git checkout -b feature/your-feature-name

# Continue working normally
git add -A
git commit -m "feat: description of your work"
git push origin feature/your-feature-name
B
Scenario B — Using Git but have uncommitted / extra local changes
Local

You have local changes that are NOT yet committed — either new files or modified files. You want to preserve this extra work and also sync with release. Use stash to temporarily save your work, pull release, then restore it.

bash / powershell — stash your changes first 
# Save all uncommitted changes (tracked + new files) to stash
git stash push -u -m "my-wip-before-release-sync"

# Verify stash is saved
git stash list
bash / powershell — sync with release 
# Fetch and switch to release
git fetch origin
git checkout release
git pull origin release

# Create your working branch
git checkout -b feature/your-feature-name
bash / powershell — restore your stashed work 
# Restore the stashed changes onto your new branch
git stash pop

# If there are conflicts, resolve them, then:
git add -A
git commit -m "wip: restored local work on top of release"
💡 git stash push -u includes untracked new files too. Without -u, new files you haven't added yet won't be stashed.
C
Scenario C — Code is NOT under git at all (no .git folder)
Local

Your local project folder has no git history. You need to safely back up your extra work, initialize git, pull from release, then bring your changes back in.

bash / powershell — Step 1: back up your extra work 
# Copy your project folder to a safe backup location first
# Windows example:
xcopy C:\path\to\your-project C:\Backup\project-backup-<date> /E /I

# Linux/Mac example:
cp -r /path/to/your-project ~/backup/project-backup-<date>
bash / powershell — Step 2: clone release into a fresh folder 
# Clone only the release branch into a new folder
git clone --branch release --single-branch <REPO_SSH_OR_HTTPS_URL> project-release

# Enter the folder and create your working branch
cd project-release
git checkout -b feature/your-feature-name
bash / powershell — Step 3: copy your extra work in 
# Manually copy over only the files YOU changed or added
# from your backup folder into the new project-release folder
# Do NOT copy .env, node_modules, vendor — those come from release

# Then commit your extra work
git add -A
git status   # review what's changed
git commit -m "feat: brought in local work from pre-git setup"
git push origin feature/your-feature-name
⚠️
Don't overwrite .env or config files from your backup. The release branch has the correct server-synced configs. Only bring in your feature files.
D
Merging your extra work back into release (when ready)
Local

Once your extra work is committed on a feature branch and tested, merge it back into release. Never commit directly to release — always go through a feature branch.

bash / powershell — merge feature into release 
# Make sure release is up to date first
git checkout release
git pull origin release

# Merge your feature branch
git merge feature/your-feature-name

# Resolve any conflicts, then push
git push origin release
bash / powershell — OR via pull request (recommended) 
# Push your feature branch to GitHub
git push origin feature/your-feature-name

# Then open a Pull Request on GitHub:
# base: release  ←  compare: feature/your-feature-name
# Get a review, then merge via GitHub UI
✅ PR merges are preferred — they keep a clear history of who changed what and allow code review before anything hits release.
✓

Completion Checklist

Verify everything is done correctly

Server Setup

  • Backup exists with timestamp
  • .gitignore excludes .env & certs
  • Uploads & storage/views untracked
  • Git initialized or existing
  • Server code committed

GitHub Connection

  • Deploy key generated on server
  • Public key added to GitHub repo
  • SSH config alias created
  • SSH test returns "successfully authenticated"
  • Remote set to SSH alias URL

Branch & Push

  • On release branch locally
  • Force pushed to origin/release
  • Upstream tracking set
  • git status shows clean

Developer Sync

  • Local release reset to origin/release
  • New feature branches from release
  • Extra local work stashed or backed up
  • Untracked code cloned fresh from release
  • PRs merge feature → release
  • Server pulls from release
🎉
Setup complete! Server code is now version controlled. All future changes should be committed and pushed. Use git pull origin release on server to deploy updates.
